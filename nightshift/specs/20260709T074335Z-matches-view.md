# matches-view

## Goal
Give a signed-in listing owner a single `/matches` page that shows the actual compatible
listings across ALL their active partnership/seeking posts, not just a per-listing count —
the natural next slice of the long-running "Compatibility matching engine" backlog item
(BACKLOG.md ~line 1549: "Surface … a `/matches` view").

## Scope
- `src/lib/matchingQuery.ts`: refactor `countMatchingSeekersForPartnership` /
  `countMatchingPartnershipsForSeeker` so the actual filtered-and-radius-checked list is
  computed once and reused — add `getMatchingSeekersForPartnership(partnership)` and
  `getMatchingPartnershipsForSeeker(seeker)` returning the matching rows (not just a count).
  Existing count functions become thin wrappers (`(await getMatching...(...)).length`) so
  every existing call site (`/listings`, the two detail pages) is behavior-identical.
- New `src/app/matches/page.tsx` (owner-gated, `redirect('/auth?next=/matches')` when signed
  out): for the signed-in user's own active partnerships + seeking listings, render one
  section per *own listing that has ≥1 match* — a small header ("Matches for your {label}")
  + up to 6 sample matching listings as a card grid (reuse `PartnershipRailCard` for
  partnership matches, `SeekerRailCard` for seeker matches — both already exist and take a
  single item prop) + a "Browse all N →" link built from the existing
  `seekerBrowseHrefForPartnership` / `partnershipBrowseHrefForSeeker` helpers.
- Empty state (no owned listings, or none with any match) — honest, no fabrication, points
  back to `/post` or `/listings`.
- Add a "View all your matches →" link at the top of `/listings` (only rendered when the
  owner has ≥1 total match across their listings) pointing to `/matches`.
- No schema change. No new dependency.

## Acceptance criteria
- `/matches` redirects a signed-out visitor to `/auth?next=/matches`.
- Signed in with 0 owned listings or 0 total matches → clean empty state, no error.
- Signed in with ≥1 owned listing that has ≥1 real match → renders that listing's real
  matching cards (via existing rail card components) + a working "Browse all N" link.
- `countMatchingSeekersForPartnership`/`countMatchingPartnershipsForSeeker` return the exact
  same numbers as before the refactor (existing `/listings` badges + detail-page nudges
  unaffected).
- `npx tsc --noEmit` and `npx next build` clean.
- QA smoke passes (HTTP 200, no console errors, no horizontal overflow) at desktop 1280 +
  mobile 375 on `/matches` (signed-out redirect target `/auth`) and `/listings`.

## Out of scope
- New-match email alerts (the other remaining named slice of this backlog item) — a
  separate, bigger lift (needs a digest/cron design) left for a future cycle.
- Aircraft-for-sale side of matching (this engine only covers partnerships ↔ seekers,
  matching the existing scope of `isCompatibleMatch`).
- Any nav/header change beyond the one `/listings` link.
