# alert-reply-to

## Goal
Make alert emails replyable: pass a real `reply_to` address to Resend on every alert
send when configured, and add a quiet "Question about a listing? Just reply to this
email." footer line to the two digest builders, so replying to an alert email no longer
dead-ends at an unmonitored from-address.

## Scope
- `src/lib/email.ts`:
  - `sendEmail`: read an optional `ALERTS_REPLY_TO` env var and pass it as Resend's
    `reply_to` field on every send (chokepoint — covers all alert email types, not just
    digests). No-op (omitted) when unset, exactly like `RESEND_API_KEY`'s existing
    no-key fail-soft.
  - `buildAlertDigestEmail` and `buildCombinedAlertDigestEmail`: render a new quiet
    footer line — "Question about a listing? Just reply to this email." — in both HTML
    and text bodies, **only** when `ALERTS_REPLY_TO` is set (read per-call, not at
    module load, so it stays unit-testable and never falsely invites replies nobody
    monitors).
- `src/lib/email.test.ts`: unit tests for the new footer line (present when the env var
  is set, absent when it isn't) on both builders.

## Out of scope
- No env var value is set here — per FREEZE, `.env*` is never edited; the human sets
  `ALERTS_REPLY_TO` whenever a monitored inbox exists. Until then this is inert (exactly
  today's behavior).
- Not touching `buildAlertConfirmEmail`, `buildPriceDropEmail`, or the other non-digest
  builders — the backlog item scopes the footer line to "the digest builders"
  specifically; `sendEmail`'s `reply_to` passthrough already covers every send type at
  the one chokepoint, so no other builder needs a per-type change.
- No schema/DB change.

## Acceptance criteria
- `sendEmail` includes `reply_to` in the Resend request body iff `ALERTS_REPLY_TO` is a
  non-empty env var; omitted (not `undefined`/empty string) otherwise.
- `buildAlertDigestEmail`'s HTML and text both contain the reply footer line when
  `ALERTS_REPLY_TO` is set, and neither contains it when unset.
- `buildCombinedAlertDigestEmail`'s HTML and text both contain the reply footer line
  when `ALERTS_REPLY_TO` is set, and neither contains it when unset.
- No other builder's output changes.
- `npx tsc --noEmit` and `npx next build` both pass.
- Full test suite passes, including the new footer-line tests.
- QA smoke gate passes on the affected pages (non-visual — no rendered UI changed, only
  server-composed email HTML/text).
